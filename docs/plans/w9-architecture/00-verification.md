## Candidate 3: Lossy Analysis (resolved by code reading)

### Question
After double-click rename via the image edit plugin, does the webviewUri leak into the file?

### Trace

1. User double-clicks image, edits path, triggers rename
2. Host (`requestImageRename.ts`) renames file on disk, writes new path into document, sends `imageRenameResponse` with `webviewUri`
3. Host sets `pendingEdit=true` (line 83), applies edit (line 91), clears in microtask (line 93) **WITHOUT calling `updateWebview()`** (by design, per header comment)
4. The `onDidChangeTextDocument` listener (provider line 121-128) fires but `pendingEdit` is true, so it does NOT call `updateWebview()`. No `update` message sent.
5. Webview receives `imageRenameResponse`, calls `handleImageRenameResponse` (image-edit-plugin.ts:561)
6. Plugin mutates `currentImageMap`: `delete currentImageMap[pending.oldPath]` (574), `currentImageMap[newPath] = webviewUri` (578)
7. **Plugin does NOT increment `imageMapVersion`** (it cannot, it's a local variable in main.ts)
8. Plugin calls `updateEditorNode` (581) which dispatches a ProseMirror transaction via `dispatch(tr)` (433)
9. **`updateEditorNode` does NOT set `isUpdatingFromExtension = true`** (only `updateImageNodeSrc` in main.ts does that, line 465)
10. Therefore `onUpdate` fires, `isUpdatingFromExtension` is false, `debouncedPostEdit()` runs
11. `debouncedPostEdit` calls `serializeEditorBody()` which calls `transformForSave`
12. `transformForSave` (line 417-428) checks `cachedReverseImageMapVersion !== imageMapVersion`
13. Since `imageMapVersion` was NOT bumped, the cached reverse map is reused
14. The new webviewUri-to-path mapping is NOT in the cached reverse map
15. `replaceImagePaths` fails to replace the new webviewUri with the relative path
16. **The webviewUri leaks into the `edit` message sent to host**

### Counterevidence evaluation

The review noted "counterevidence: cache reverse has existed since c97c9a3 (2026-03-28), and manual rename testing passed". This can be explained by:
- If the host sends an `update` shortly after (e.g., from a subsequent save or external change), the map gets rebuilt with version++, masking the window of vulnerability
- The race window is narrow: between `handleImageRenameResponse` and the next `update` or save
- Manual testing may not have checked the exact markdown file content during the race window

### Conclusion

The lossy path is **confirmed by code reading**. No `imageMapVersion++` exists anywhere outside `main.ts`, and the plugin modifies the shared map object without any way to signal staleness to the cache. The bug requires: (1) rename via double-click, (2) debounced edit fires before the next `update` from host. Both are normal conditions in the rename flow.

**This is a bug. A verification ticket is not needed: the code path is unambiguous. A bug fix should precede any refactoring of the image map module (candidate 3).**
